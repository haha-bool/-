# 个人外贸操作系统 · 产品分析与架构

> 版本：v0.2（第二阶段：CRM / 报价 / 文档 / 岗位能力与每日推荐 已实现）  
> 日期：2026-10-20

---

## 1. 对用户与业务目标的理解

### 1.1 你是谁（系统如何定位你）

- 本科在读，已过四级（425+），六级计划 2026-12。
- 一年多的校园商业实践：劳务中介、电话卡、床上用品、驾校、直播/短视频流量、校园代理。
- **有真实交易经验，但没有外贸专业经验**；不是零基础小白，也不是成熟业务员。
- 2028 年前后去广州（备选深圳），目标岗位：初级外贸业务员 / 海外客户开发 / 外贸助理。
- 长期目标：先就业实现经济独立，再逐步走向自己的业务。

系统对你采取的态度是：**"有商业直觉的学徒"**——不重复讲"什么是客户"，但会要求你把每个术语落到一张真实订单里算清楚。

### 1.2 你真正的痛点（不是"缺一个仪表盘"）

| 表面需求 | 真实问题 | 系统的应对 |
| --- | --- | --- |
| 学外贸 | 知识碎片化，记住了术语但不会用 | 每条知识必须有"使用场景 + 常见错误 + 检查清单" |
| 学英语 | 四级能过，但写不出开发信 | 只练真实业务场景，先写后改，不喂范文 |
| 做计划 | 计划很满、执行三天 | 每日模板 + 单 P0 + 不做不补 + 每周半天空白 |
| 找方向 | 不知道离岗位差多少 | 目标 → 里程碑 → 任务三级拆解，里程碑可验证 |
| 容易自责 | 项目出问题就全揽到自己身上 | 复盘强制区分"我的决策责任 / 外部因素" |

### 1.3 产品目标（按优先级）

1. 让"今天做什么"不再需要决策——打开就有 6 项以内的计划。
2. 让知识从"看过"变成"能用"——掌握度、场景、检查清单、复习自测。
3. 让英语练习围绕真实业务，而不是考试题。
4. 让每一次踩坑变成规则，而不是情绪。
5. 两年后能从中导出**可验证的求职证据**（邮件、报价、复盘、订单流程）。
6. 信息不足时明确说"不知道"，绝不编造数据。

### 1.4 明确不做的事

- 不做"AI 一键生成业绩/简历包装"。
- 不把模拟项目伪装成真实成交。
- 不在第一阶段塞入需要外部账号的功能（Shopee API、海关数据、客户数据库）。
- 不做多人协作、云同步（个人系统，本地优先）。

## 3. 核心页面与用户操作流程

### 3.1 页面清单

| 路由 | 页面 | 主要操作 |
| --- | --- | --- |
| `#/` | 驾驶舱 | 生成今日计划、勾选任务、打卡、跳转各模块 |
| `#/tasks` | 今日任务 | 切换日期、生成计划、新增/编辑/删除、完成、顺延 |
| `#/knowledge` | 知识库列表 | 搜索、分类筛选、进入详情、新建 |
| `#/knowledge/:id` | 知识详情 | 阅读、掌握度、笔记、标记已核实、关联、编辑、删除 |
| `#/english` | 训练室 | 场景库/练习记录/错误本/表达库切换、开始练习 |
| `#/english/:id` | 练习详情 | 写作、保存草稿、提交自检、看检查与结构、复制 AI 提示词、记错误/表达 |
| `#/plan` | 目标与项目 | 切换里程碑、增改目标、增改项目、添加里程碑 |
| `#/review` | 复盘 | 写日/周/项目复盘、展开历史 |
| `#/settings` | 设置 | 档案、导出、导入、快照、模板开关与新增 |

### 3.2 典型流程

**每天（3 分钟）**
```
打开驾驶舱 → 生成今日计划 → 按 P0/P1 顺序做 → 勾选 → 晚上写 10 分钟复盘 → 补记分钟
```

**学一条新知识**
```
知识库 → 新建条目（通俗/专业/场景/示例/错误/清单）→ 设掌握度=1 → 3 天后自测 → 改掌握度
```

**练一封开发信**
```
英语训练室 → 选场景 → 读背景与任务 → 自己写 → 提交 → 看本地检查 → 勾自检
→ 复制 AI 反馈包到 AI → 把修改点记进错误本 → 好句子存表达库
```

**做一次复盘**
```
复盘 → 选类型 → 按十问填写（事实 → 责任 → 规则）→ 保存 → 把规则抄进知识库检查清单
```

**里程碑推进**
```
目标与项目 → 勾选里程碑 → 目标进度自动变化 → 驾驶舱同步显示
```

## 4. 数据模型与实体关系

### 4.1 实体关系

```
goals 1 ──── n milestones
  │                 │
  │                 └── (完成数/总数 ⇒ goals.progress)
  │
  ├── n projects
  │        │
  ├── n tasks ── n? (task.template_id → task_templates)
  │        └── category ∈ {english, trade, project, review, admin}
  │                 └── 完成分钟 ⇒ daily_log.auto_english / auto_trade
  │
  └── n reviews（按 kind: daily/weekly/project）

knowledge 1 ──── n knowledge_links ──── 1 knowledge（多对多，双向展示）
knowledge 1 ──── n english_sessions?（弱关联：session 引用场景 key）
english_sessions 1 ──── n error_log（错误来自某次练习）
english_sessions 1 ──── n expressions（好句子来自某次练习）

daily_log（按日期唯一）← 手动打卡 + 任务自动累计
meta（key-value）：schema_version / seeded_at / profile / last_started_at
```

### 4.2 关键字段（节选）

| 表 | 关键字段 | 设计理由 |
| --- | --- | --- |
| `goals` | title, why, metric, target_date, progress | "为什么"和"怎么衡量"必须写下来，否则目标会漂移 |
| `milestones` | goal_id, title, due_date, status | 目标进度只认里程碑，不认手填百分比 |
| `projects` | kind(real/sim/practice/study), status, risks, result | 真实/模拟必须可区分，避免把模拟当业绩 |
| `tasks` | priority, status, plan_date, estimate_min, done_criteria, template_id | 完成标准 + 预计耗时，才能判断"做了没有" |
| `task_templates` | cadence, weekday_mask, active | 每日节奏可调，不改历史任务 |
| `knowledge` | plain, pro, scenario, example, pitfalls, checklist, source_name, verified_on, trust, mastery | 把"定义"扩展成"可用性"；动态信息必须带核实日期 |
| `knowledge_links` | from_id, to_id, rel | 概念之间要能顺着链条复习 |
| `english_sessions` | scenario_key, user_answer, self_check, status | 保留原始作答与自检，不覆盖 |
| `error_log` | kind, wrong, correct, rule, hits | 重复出现的错误才值得背 |
| `expressions` | en, zh, note, category | 可复用句库 |
| `reviews` | 十问字段 + rule_text + mood | 复盘必须产出规则；mood 可选，不做评分 |
| `daily_log` | english_min + auto_english, trade_min + auto_trade, note | 手动补记与任务自动累计分开，避免互相覆盖 |

### 4.3 未实现但已预留

`clients` / `contacts` / `follow_ups` / `products` / `suppliers` / `quotes` / `quote_lines` / `documents` / `risks` / `job_skills`。
第二阶段直接加表 + 迁移即可，现有 `schema_version` 与迁移机制已就位。

## 6. 技术选型与理由

| 选择 | 理由 | 代价 / 边界 |
| --- | --- | --- |
| **Node.js 内置 HTTP + `node:sqlite`** | 零第三方依赖，`npm install` 都不需要；离线可用；SQLite 单文件易备份 | `node:sqlite` 在 Node 22 仍标注 experimental；要求 Node ≥ 22.5，并在文档中写明 |
| **原生 ES Modules + 手写 CSS** | 没有构建步骤，改一行刷新即见；两年后仍然能直接跑 | 代码量比框架多；复杂交互（拖拽、虚拟列表）后期需要引入库 |
| **单页 + hash 路由** | 刷新不丢状态；本地文件服务即可 | 无 SSR（不需要） |
| **SQLite 而非 JSON 文件** | 关系、聚合、事务、索引；数据量长大后仍稳 | 迁移需写 ALTER；已内置轻量迁移 |
| **任务模板引擎** | 把"每日节奏"变成可调数据，而不是硬编码 | 模板只能按星期，暂不支持"每 3 天" |
| **AI 以"提示词包"方式接入** | 不绑死某家 API、不需要 Key、不产生费用；批改质量取决于你用的模型 | 无法自动回填批改结果（第二阶段可加 API Key 配置） |
| **JSON 导出/导入 + 启动快照** | 换电脑、迁移、误删恢复 | 不是实时同步；需手动备份 |

**为什么不选 Electron / Tauri**：当前形态（本地服务 + 浏览器）已经满足"本地、可离线、双击启动"，且体积最小、最容易长期维护。若以后要托盘图标/开机自启，再加一个轻量壳。

## 7. 主要风险与依赖条件

| 风险 | 影响 | 当前应对 | 后续动作 |
| --- | --- | --- | --- |
| Node 版本升级导致 `node:sqlite` API 变化 | 服务起不来 | 文档标明 Node ≥22；数据可导出 | 如遇不兼容，切换 `better-sqlite3`（需 npm 安装），schema 不变 |
| 数据只在本机 | 硬盘损坏/误删即丢失 | 启动与退出自动快照、手动导出 | 每周日导出到网盘（文档已写） |
| 知识条目内容随政策变化 | 用错关税/费率导致报价亏损 | 动态条目 `trust=dynamic`，带核实日期，驾驶舱提示待核实 | 第二阶段的报价器强制填写"核实日期" |
| 英语训练无自动批改 | 语法错误可能被固化 | 本地启发式检查 + AI 提示词 + 错误本 | 第二阶段可选接入模型 API，需用户自备 Key |
| 计划过载（学生课业冲突） | 连续断档 → 放弃 | 单 P0、不做不补、任务量控制表 | 每周复盘检查断档原因 |
| 目标进度只看里程碑 | 日常工作推进不体现在百分比 | 驾驶舱同时显示任务完成与学习分钟 | 第二阶段可加"证据数"维度（邮件数、报价数） |
| 模拟项目被误当真实业绩 | 求职时失真 | 项目 `kind` 标记 + 界面徽章 | 作品集导出时强制标注 |
| 单用户、无并发控制 | 同时开两个窗口编辑同一条会互相覆盖 | 本地单用户场景，风险极低 | 如需多人，升级为服务端版本 |

**外部依赖**：无。所有功能离线可用。
**未接入**：海关数据、汇率 API、Shopee 开放平台、AI 模型 API、邮件客户端。
